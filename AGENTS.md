# Соглашения для исполнителей notification-service

Канон соглашений репозитория для исполнителя любого вендора и для человека.
`CLAUDE.md` — одна строка `@AGENTS.md`; машиночитаемая часть (соседи, установка,
тестовые сервисы, проверки) — [`.agents/runner.yaml`](.agents/runner.yaml), формат —
`runner_config.md` рядом с `control_plane_agent` в control-plane. Демон исполнителя
читает `runner.yaml` только с базовой ревизии задачи: правка файла на ветке задачи
действует после ревью и вливания.

Что это за сервис и как он устроен — [README.md](README.md) и ADR в
[docs/adr/](docs/adr/README.md); порядок вклада — [CONTRIBUTING.md](CONTRIBUTING.md).

## Среда

- Рабочая копия — текущий каталог (`notification-service`). Соседи
  `../platform-auth-sdk`, `../control-plane` и `../iam-service` стоят на ревизиях,
  закреплённых суперпроектом, и доступны **только для чтения**: изменённый сосед
  проваливает прогон (`neighbour_modified`).
- Дизайн фичи — `specs/notifications/` суперпроекта (spec, plan, tasks); в рабочей
  копии его нет, читай из суперпроекта.
- **Контракт другого сервиса не выдумывай.** Вызовы Control Plane — через клиент
  `../control-plane/client` и схемы `../control-plane/src/control_plane/api/v1/schemas.py`;
  IAM — по коду `../iam-service`. Закрепляй contract-тестами против их моделей.
- Проверка токенов — только через `platform-auth-sdk`, заново не писать (ADR-0030
  суперпроекта).
- Сервис нейтрален к домену: никаких понятий конкретного бизнеса в коде; типы и
  тексты уведомлений приходят от отправителя.
- Тестовая PostgreSQL выдаётся на прогон (сервис `db` в `runner.yaml`), адрес — в
  `NS_TEST_DATABASE_URL`. Docker внутри нет. Внешние API (Telegram Bot API, SMTP) в
  тестах — фейками по их документированному контракту.
- Тестовая база одна на прогон: **одновременно — только один прогон тестов**, и не в
  фоне. `make test` держит блокировку `.pytest.lock`: второй запуск в той же копии
  сразу завершается с сообщением `tests are already running` — рецепт выходит с
  кодом 75, а сам `make` возвращает 2, как при любой ошибке рецепта. Прогон молчит
  дольше нескольких минут — останови его и разберись, а не запускай новый.

## Команды

Эти цели зовут `checks` в `runner.yaml`, и их же должен звать CI — job'а в
суперпроекте пока нет; команды не копируй, вызывай цели.

| Цель | Что делает |
|---|---|
| `make install` | `uv sync --locked` — зависимости по `uv.lock`, соседи — путём; отставший lock — ошибка, обнови его `uv lock` |
| `make lint` | `ruff check` и `ruff format --check` |
| `make fmt` | исправить то, что `ruff` умеет сам |
| `make migrations-check` | ровно одна голова alembic |
| `make test` | `pytest` на `NS_TEST_DATABASE_URL`; `PYTEST_ARGS="tests/test_app.py -x"` — выборочно |
| `make check` | всё перечисленное — то, что должен звать CI |

## Правила

- Архитектурные решения — в ADR (`docs/adr/` сервиса; решения уровня платформы — ADR
  суперпроекта). Меняешь контракт API, схему БД или поведение, описанное в ADR, —
  обнови или дополни ADR в том же коммите.
- Номер нового ADR — следующий свободный в `docs/adr/` на `origin/<baseBranch>`
  (см. «Перед сдачей», п. 1) на момент коммита: параллельные ветки уже занимали
  один номер.
- Документация — на русском; комментарии в коде — английские, имена API и сущностей —
  на английском.
- Не коммить секреты, локальные абсолютные пути, `.env`, артефакты сборки.
- Не трогай `main` и чужие ветки: ветку задачи коммитит и публикует демон.
- Не делай того, чего нет в задаче. Найденное попутно — в отчёт, а не в код.

## Перед сдачей (обязательно)

Каждый пункт уже стоил круга ревью; сдача без них — возврат задачи.

1. Целевая ветка — `baseBranch` задачи, нет — `main`. Рабочая копия — worktree голого
   зеркала, простой `git fetch` двигает только `FETCH_HEAD`, поэтому:
   `git fetch origin +refs/heads/<baseBranch>:refs/remotes/origin/<baseBranch>`.
   Сливай и сравнивай только с `origin/<baseBranch>`: ушла вперёд — `git merge
   origin/<baseBranch>` и разреши конфликты; проверка —
   `git merge-tree --write-tree origin/<baseBranch> HEAD` без конфликтов.
2. На дереве слияния — `make check` (линтеры, одна голова alembic, полный прогон тестов
   на `NS_TEST_DATABASE_URL`). Сборку Docker-образа не делай.
3. Доработка после отклонения: каждый сценарий из комментария ревью сначала
   воспроизведи тестом, падающим на прошлой попытке, и только потом исправляй.
4. Граничные случаи новой логики — отдельными тестами: пустое, `null`, неверный тип,
   повтор и идемпотентность, параллельные вызовы, пути файловых операций.
5. Безопасность: невидимый или чужой объект — ответ, неотличимый от отсутствующего,
   если так требует ADR; секреты не попадают в журналы и ответы.

В отчёте — перечень проверок по пунктам 1–5: команда и результат.

## Отчёт

Первой строкой — что сделано, одной фразой. Дальше: изменённые места, какие тесты
прогнаны и с каким результатом, что осталось или требует решения человека. Ревью
делает человек, поэтому отчёт должен позволять проверить работу без повторного
исследования.
