# ADR-0005. Правила уведомлений как данные: `NotificationRule`

Статус: принято (2026-09-27), задача C003 фичи `declarative-cycle`
(TASK-000659, повтор TASK-000642). В документе задач фичи и в TAI-ADR-0053 это
решение названо «ADR-0003 notification-service»: номер 0003 в сервисе уже
занят, следующий свободный — 0005.

Основание: `specs/declarative-cycle/` суперпроекта (spec — FR-011, FR-012,
FR-013, FR-016, FR-017, сценарий 4; plan — «Исследование» Р4, «Дизайн →
notification-service», «Переход»; tasks — C003, C007, C011, C012),
TAI-ADR-0053 п. 4 (решение владельца 2026-09-27, отступление по ст. VIII
конституции принято), форма спецификации — `$defs.notificationRuleSpec` в
`packages/schema/v1/object.schema.json` суперпроекта (C001, ветка
`feature/declarative-cycle`, `b8d6d11`). Грамматика условий — CP-ADR-0063 §2,
каталог событий — CP-ADR-0068 (`docs/events/catalog.json` ядра).

Заменяет: таблицу «События → уведомления» и фильтр потребителя из
[ADR-0002](0002-control-plane-event-consumer.md) — после перехода (п. 8).
Остальное в ADR-0002 (чтение журнала, курсор, отправитель, барьеры
дедупликации, закрытые действия) действует.

## Контекст

Какие события ядра становятся уведомлениями, кому, каким текстом и с какими
кнопками — сейчас код сервиса: `EVENT_TYPES`, `CLOSING` и обработчики
`events.CoreEventHandler` (ADR-0002). Новый вид уведомления требует выпуска
сервиса. Каналы, настройки получателя, тихие часы, обязательные правила и
группы уже данные сервиса — не хватает только «что превращается в
уведомление». В дизайне notifications отдельный вид каталога был отвергнут для
первой версии; владелец 2026-09-27 решил его ввести (TAI-ADR-0053).

## Решение

### 1. Вид каталога `NotificationRule`

Правило — объект пакета каталога (TAI-ADR-0044): `apiVersion: taimen.ai/v1`,
`kind: NotificationRule`, `key` — ключ правила (`^[a-z0-9][a-z0-9._-]*$`, до
128 символов, как у `WorkRule`), `spec` — `notificationRuleSpec`. Источник
формы — схема суперпроекта (C001); сервис держит её копию
`src/notification_service/contracts/notification-rule.schema.json` — дословно
`$defs.notificationRuleSpec` с добавленным `$schema` (sha256 канонического JSON
без `$schema`, ключи отсортированы, без пробелов:
`76563093d8bf5e2e5b2e37f2d75f14dc001c606e16030c84bca30b88ba062bf4`). Форму
спецификации меняет только схема суперпроекта; копия обновляется в том же
цикле, что и правка схемы.

Спецификация:

| Поле | Смысл |
|---|---|
| `on.type` | Тип события каталога ядра (`approval.requested`) или префикс (`approval.*`) |
| `on.when` | Условие грамматики правил ядра (CP-ADR-0063 §2) с корнями `payload`, `event`, `task`; по умолчанию `true` |
| `recipient` | Кому: `kind` и, для части видов, `ref`, `workspace`, `fallback` (п. 3) |
| `notification.type` | Тип создаваемого уведомления: по нему работают настройки получателя и обязательные правила |
| `notification.title`, `body` | Шаблоны заголовка и текста (п. 4) |
| `notification.links` | До 5 ссылок `{label, url}`, оба — шаблоны |
| `notification.actions` | `[approvalDecide]` — кнопки «Одобрить»/«Отклонить» решения |
| `dedupKeyTemplate` | Шаблон ключа дедупликации уведомления; по умолчанию `rule:<key>:event:{{event.id}}` |
| `close.on`, `close.outcome` | Какие события закрывают кнопки уведомления с тем же ключом и каким исходом |
| `status` | `enabled` (по умолчанию) или `disabled` — правило хранится, но не исполняется |
| `description` | Текст для людей |

`additionalProperties: false` на каждом уровне: неизвестное поле спецификации
— отказ проверки (п. 6).

В YAML пакета ключ `on` пишется в кавычках (`"on":`): загрузчики YAML 1.1
(`yaml.safe_load`, которым читает пакеты `tools/cp_packages.py`) читают
голый `on` как `true`, и спецификация теряет обязательное поле. Выгрузка
установщиком (C011) обязана так же кавычить этот ключ.

### 2. Исполнение

Потребитель событий остаётся тем же (`EventConsumer` SDK ядра, курсор и
`handled_events` — ADR-0002), меняется только фильтр и обработчик:

- **Фильтр** — объединение `on.type` и `close.on` действующих правил со
  статусом `enabled`; префикс `x.*` передаётся ядру как `x.`. Нет ни одного
  такого правила — потребитель не запускается и событий не читает (FR-012).
  Набор правил меняется (п. 5) — потребитель перезапускается с тем же курсором
  на новом фильтре в течение одного цикла опроса (`NS_EVENTS_POLL_SECONDS`).
  События, которые ядро отдало по старому фильтру и которые новые правила уже не
  описывают, пропускаются: уведомления об истории не рассылаются.
- **На событие** — все подходящие правила по порядку ключей: `on.type`
  совпадает, `on.when` истинно. Каждое подходящее правило даёт не больше одного
  уведомления; ошибка одного правила (адресат не найден, ошибка оценки условия)
  пишется в лог с ключом правила и не мешает остальным — как «событие
  пропускается» в ADR-0002. Недоступность ядра или каталога адресатов — отказ
  обработки события целиком, SDK повторяет его.
- **Закрытие** — событие, тип которого есть в `close.on` правила: сервис
  рендерит `dedupKeyTemplate` этого правила над закрывающим событием и
  закрывает действия уведомления сервиса с этим ключом (`close_actions`,
  ADR-0002 «Закрытые действия»): `actionsOutcome = {status, by, channel, at}`,
  где `status` — `close.outcome` (по умолчанию — последний сегмент типа
  события: `approved`, `rejected`, `cancelled`), `by` — `event.actorId`,
  `channel` — `payload.channel`, `at` — `event.occurredAt`. Побеждает первое
  закрытие; нет уведомления — ничего. Ключ дедупликации поэтому должен
  выводиться из того, что общее у открывающего и закрывающего событий (для
  решений — `event.entityId`, id approval).
- **Отправитель, барьеры дедупликации, адресация, выбор каналов, журнал
  доставки** — как в ADR-0002: уведомление создаёт сам сервис своим service
  account'ом через `NotificationSender.accept` с ключом из `dedupKeyTemplate`.
- **Версия правила** — событие обрабатывается действующими на момент обработки
  версиями; уже созданные уведомления не меняются ни при новой версии, ни при
  выводе правила из оборота (сценарий 4, приёмка 3). Кнопки уже отправленного
  уведомления закрываются по `close` той версии, которая действует при
  закрывающем событии.

### 3. Адресат

| `recipient.kind` | Кто получает |
|---|---|
| `assigned` | Назначенный решающий, как его объявляет событие: principal по пути `ref` (по умолчанию `payload.assignedPrincipalId`); путь пуст — держатели роли `payload.requiredRoleId` в workspace (`workspace`, по умолчанию `payload.workspaceId`, иначе `event.workspaceId`). Это прежняя адресация `approval.requested` |
| `role` | Держатели роли, id которой по пути `ref`, в workspace по пути `workspace` (по умолчанию `event.workspaceId`) |
| `taskOwner` | Владелец задачи события (`task.ownerId`) |
| `taskAssignee` | Исполнитель задачи события (`task.assigneeId`) |
| `principal` | Конкретный principal: `ref` — UUID. `${ПЕРЕМЕННАЯ}` установки подставляет установщик пакетов до применения; сервис хранит и принимает только UUID |

`fallback` (`taskOwner`, `taskAssignee`, `none` — по умолчанию) — второй
адресат, если первый пуст (путь не даёт значения, у задачи нет владельца).
Адресата нет и после `fallback` — уведомление не создаётся, в лог пишется ключ
правила и id события. Роль без держателей — как и сейчас, запись в журнале
доставки без адресатов (edge case spec). Principal или роль неизвестны каталогу
ядра (`422 unknown_recipient`) — событие для этого правила пропускается.

### 4. Шаблоны и корни данных

Шаблон — строка с плейсхолдерами `{{ путь }}`, грамматика путей — CP-ADR-0063
§2 (`корень(.сегмент)*`, сегмент `[A-Za-z0-9_-]{1,64}`, индекс списка —
число). Никаких условий, циклов, вызовов и фильтров. Корни:

| Корень | Что это | Откуда |
|---|---|---|
| `payload` | Тело события | Событие журнала, схема `(type, schemaVersion)` каталога |
| `event` | Конверт события: `id`, `type`, `entityType`, `entityId`, `workspaceId`, `actorId`, `occurredAt`, … | Поля `envelope` каталога |
| `task` | Проекция задачи ядра (`TaskOut`: `id`, `publicId`, `title`, `status`, `ownerId`, `assigneeId`, `typeKey`, `customFields`, …) | `GET /tasks/{id}` по `event.entityId` для `entityType = task`, иначе по `payload.taskId`; читается, только если правило обращается к корню `task` |

Дополнительно путь, который заканчивается сегментом `displayName` после
идентификатора principal'а (`{{payload.requestedBy.displayName}}`,
`{{event.actorId.displayName}}`, `{{task.ownerId.displayName}}`), подставляет
имя principal'а из `GET /principals/{id}` (`PrincipalOut.displayName`) — так
прежний текст «Запрашивает: <имя>» переносится без логики в шаблоне. Имя не
прочиталось — пусто.

Правила подстановки:

- значение отсутствует (`null`, нет поля, задача не читается) — пустая строка;
  скаляр — его текст; объект и список — не подставляются (отказ проверки при
  записи, если схема каталога говорит, что по пути объект или список);
- в `title` управляющие символы и переводы строк сворачиваются в пробел, длина
  — до `MAX_TITLE`, в `body` — до `MAX_BODY` с многоточием, как у
  `_line`/`_text` сейчас;
- строка `body`, в которой были плейсхолдеры и все они дали пусто, опускается
  целиком (так необязательные строки «Комментарий: …» исчезают, как прежде);
  заголовок после подстановки пуст — вместо него `notification.type`;
- ссылка опускается, если хоть один плейсхолдер её `url` дал пусто или
  результат — не абсолютный `http(s)` URL. База URL интерфейса — `${ПЕРЕМЕННАЯ}` установки, её
  подставляет установщик пакетов (топология окружения в пакет не пишется);
  `NS_TASK_URL_TEMPLATE` после перехода не используется;
- секретов шаблон не видит: корни — только поля события и проекции задачи, в
  которых ядро уже редактирует материал, похожий на секреты (FR-017).

`approvalDecide` строит прежние действия `approve` и `reject` с
`data = {kind: "approval.decide", approvalId, decision}`, `approvalId` —
`event.entityId` (у событий `approval.*` сущность — approval; в payload его
нет, хотя описание поля в схеме C001 говорит «из payload.approvalId» — на
стороне сервиса это id сущности события). Их исполняет канал с кнопками
(ADR-0003) — без изменений.

### 5. Хранение и версии

Таблица `notification_rules` (миграция `0004`, C007): `id`, `tenant_id` (IAM
tenant администратора, применившего правило), `key`, `version` (1, 2, … в
пределах ключа), `spec` (JSONB — нормализованная спецификация), `spec_hash`
(sha256 канонического JSON `spec`: ключи отсортированы, без пробелов, UTF-8),
`state` (`active` | `superseded` | `retired`), `created_by` (`sub` токена),
`created_at`. Уникальны `(tenant_id, key, version)` и одна `active` на
`(tenant_id, key)` (частичный индекс).

Версии неизменяемы. `POST` спецификации, хэш которой совпадает с действующей
версией ключа, ничего не создаёт (`200`, та же версия) — повторное применение
пакета идемпотентно. Другой хэш — новая версия `active`, прежняя
`superseded`, в одной транзакции (`201`). Вывод из оборота (`:retire`) ставит
действующей версии `retired`; `POST` в выведенный ключ заводит следующую версию
и снова делает её действующей. `status: disabled` — часть спецификации и хэша:
правило действует как версия, но не исполняется.

Потребитель читает правила своего tenant'а (tenant service account'а сервиса,
допущение ADR-0002: это IAM tenant людей того же tenant'а ядра). Правила других
tenant'ов не исполняются.

### 6. Проверка спецификации

Одна функция проверки для `POST` и `:validate`, по порядку:

1. Форма — JSON Schema копии `notificationRuleSpec` (Draft 2020-12): лишнее
   поле, неизвестный `recipient.kind`, неизвестное действие — отказ (FR-013).
2. Типы событий — по **снимку каталога событий ядра**
   `src/notification_service/contracts/catalog.json` (копия
   `docs/events/catalog.json` ядра, снят с ревизии `169e0a2`; contract-тест сверяет её с
   `control_plane.domain.event_catalog.catalog_document()` закреплённой ревизии
   ядра). `on.type` — существующий тип, префикс `x.*` — совпадает хотя бы с одним
   типом; каждый тип `close.on` существует. Иначе — `unknown_event_type`.
3. Пути условий и шаблонов (`on.when`, `title`, `body`, `links`,
   `dedupKeyTemplate`, `close.outcome`, `recipient.ref`,
   `recipient.workspace`): корень из п. 4; `payload.<поле>` — свойство
   схемы текущей версии **каждого** типа, на который правило срабатывает
   (для `close.outcome` — каждого типа `close.on`; для `dedupKeyTemplate` —
   и тех, и других); `event.<поле>` — поле `envelope`; `task.<поле>` — поле
   `TaskOut`, и корень `task` допустим, только если у каждого такого типа
   сущность `task` или в схеме есть `payload.taskId`; `…displayName` — только
   после поля с `format: uuid`, `event.actorId`, `task.ownerId`,
   `task.assigneeId`, `task.createdBy`. Вложенные пути внутрь `object` без
   `properties` (`task.customFields.x`) не проверяются глубже. Иначе —
   `unknown_field`.
4. Условие — грамматика CP-ADR-0063 §2 (операторы, глубина ≤ 16, узлов ≤ 256,
   документ ≤ 16 KiB); иначе — `invalid_condition`.
5. `actions: [approvalDecide]` — только если сущность каждого типа `on` —
   `approval`; `recipient.kind: principal` — `ref` задан и это UUID; `role` —
   `ref` задан. Иначе — `invalid_rule`.

Ответ отказа — `422 invalid_notification_rule`, конверт ошибок сервиса
(ADR-0001), в `details.errors` — все найденные ошибки
`{path, code, message}`; `path` — JSON Pointer в спецификации.

Грамматика условий исполняется в сервисе своим вычислителем (ядро не
библиотека сервиса в рантайме); contract-тест прогоняет общие примеры через
вычислитель сервиса и `control_plane.domain.work_rules` ядра и требует
одинаковых ответов и ошибок.

### 7. API (`/api/v1`, scope `notifications:admin`)

| Метод и путь | Что делает |
|---|---|
| `GET /notification-rules` (`key`, `includeRetired`, `limit`, `cursor`) | Действующие версии правил tenant'а, по ключу: `{key, version, spec, specHash, state, createdBy, createdAt}`; выгрузка установщиком пакетов |
| `POST /notification-rules` — `{key, spec}` | Применить: `201` — новая версия, `200` — спецификация не изменилась; `422 invalid_notification_rule` |
| `POST /notification-rules:validate` — `{key, spec}` | Та же проверка без записи: `200 {valid: true, specHash, changed}` (`changed` — отличается ли от действующей версии) или `422` как у `POST` |
| `POST /notification-rules/{key}:retire` | Вывести из оборота: `200` с записью (повтор — тот же ответ), `404` — ключа нет |

Маршруты — только `notifications:admin` (ст. VI конституции); отправители с
`notifications:send` их не видят. Установщик пакетов (C011) применяет вид
`NotificationRule` к сервису (`${NOTIFICATION_SERVICE_URL}`, токен audience
`notification-service`), сначала `:validate` всех правил пакета, затем `POST`;
выгрузка — `GET`, круговая выгрузка совпадает с файлами пакета (FR-016).

### 8. Переход со встроенной таблицы

1. C007 выкатывает таблицу, API, проверку и исполнение по правилам **и**
   удаляет `EVENT_TYPES`, `CLOSING` и обработчики событий — без двойного пути.
   До применения правил сервис событий не читает: курсор потребителя стоит
   там, где его оставила прежняя версия.
2. Сразу после выкатки применяется пакет `notify` с правилами прежнего
   поведения (ниже). Потребитель стартует с сохранённого курсора — события,
   пришедшие между выкаткой и применением, обрабатываются, а ключи
   дедупликации прежние (`control-plane:approval:<id>`,
   `control-plane:event:<id>`): уведомление, созданное прежней версией до
   выкатки, не дублируется, а его кнопки закрываются новым правилом.
3. Окно между шагами 1 и 2 — минуты одного деплоя; дольше его держать нельзя
   (FR-012 требует, чтобы уведомления не пропали).
4. Совместимость закрепляет тест C007: правила ниже на тех же событиях дают те
   же уведомления, что встроенная таблица, — адресат, тип, заголовок, кнопки,
   ссылка, ключ дедупликации, закрытие. Текст сравнивается по содержанию: в
   необязательных частях («(причина)») возможны различия пунктуации.

Прежнее поведение — три правила пакета `notify`. У `task.verification_failed`
два текста («вернулась в работу» и «ждёт человека»), а условий внутри шаблона
нет, поэтому это два правила с противоположными `on.when`; закрытие кнопок по
исходу решения — секция `close` правила запроса (отдельный файл
`approval-closed.yaml` из plan не нужен: закрывающее правило без своего
уведомления в схеме не выражается).

```yaml
# notify/notification-rules/approval-requested.yaml
apiVersion: taimen.ai/v1
kind: NotificationRule
key: approval-requested
spec:
  description: >-
    Назначенному решающему — запрос решения с кнопками; исход решения
    закрывает кнопки.
  "on": {type: approval.requested}
  recipient: {kind: assigned}
  notification:
    type: approval.requested
    title: "Нужно решение: {{task.publicId}} {{task.title}}"
    body: |-
      Работа: {{task.publicId}} {{task.title}}
      Запрашивает: {{payload.requestedBy.displayName}}
      Комментарий: {{payload.comment}}
    links:
      - {label: Открыть задачу, url: "${TASK_URL_BASE}/{{task.publicId}}"}
    actions: [approvalDecide]
  dedupKeyTemplate: "control-plane:approval:{{event.entityId}}"
  close:
    "on": [approval.approved, approval.rejected, approval.cancelled]
```

## Реализация (C007, TASK-000646)

Дополнение 2026-09-27; решение выше не меняется, здесь — то, что оно оставило
реализации.

- **Код.** Проверка, вычислитель условий и шаблоны — `rules.py` (чистые
  функции); версии — `rule_store.py`, таблица `notification_rules` — миграция
  `0004`; маршруты — `api.py`; исполнение — `events.py`: `RuleEventHandler`
  (обработчик SDK) и `RuleConsumer` — держит потребитель SDK на фильтре
  включённых правил и перезапускает его под тем же именем, то есть с тем же
  курсором. `EVENT_TYPES`, `CLOSING`, `CoreEventHandler` и
  `NS_TASK_URL_TEMPLATE` удалены. `jsonschema` стал зависимостью сервиса
  (проверка формы по копии `notificationRuleSpec`).
- **Коды ошибок.** Нарушение формы (п. 6.1) — код `invalid_spec`, `path` —
  JSON Pointer поля, `message` — сообщение валидатора. При ошибках формы
  остальные шаги не выполняются: по спецификации неверной формы их результат
  ничего не значит; в ответе — все ошибки формы.
- **Проекция задачи.** Сервис не импортирует ядро в рантайме, поэтому поля
  `TaskOut` и их JSON-типы — снимок `rules.TASK_FIELDS`; contract-тест
  сверяет его с моделью закреплённой ревизии ядра. Корень `event` — поля
  `envelope` каталога без `payload` (его читает корень `payload`).
- **Ключ дедупликации.** Плейсхолдер ключа, давший пусто, — правило для этого
  события пропускается с записью в лог: ключ без части склеил бы уведомления
  разных событий. Ключ длиннее 200 символов (размер `dedup_key`) — так же.
  На закрывающем событии — то же: нечего закрывать.
- **Ответы API.** `GET` — `{items, nextCursor}`, курсор — ключ последнего
  правила страницы, по умолчанию 100, не больше 500. `specHash` — sha256 в hex.
  Применение или вывод из оборота будит потребитель своего процесса сразу, не
  дожидаясь опроса; другие процессы видят перемену в течение одного опроса.
- **Правила читаются на каждое событие** из базы (версии на момент обработки,
  п. 2); задача ядра — не больше одного раза на событие и только если хоть одно
  подходящее правило читает корень `task`; имя principal'а — один раз на
  событие.
- **Совместимость** (п. 8.4) — `tests/test_notification_rules_compat.py`: правила
  этого ADR применяются через API, как их применит установщик, и на тех же
  событиях дают то, что давала таблица ADR-0002. Отличие по содержанию одно:
  причина проваленной проверки — отдельной строкой «Причина: …», а не в скобках.
  Для событий `approval.requested` версии 1 (без `requestedBy`) строки
  «Запрашивает» больше нет: таблица брала имя из `event.actorId`, правило —
  из `payload.requestedBy`.

## Отвергнуто

- **Правила ядра со скиллом `notify.send`** — нужны побочные действия в
  правилах ядра (запрещены), доставка зависела бы от живого исполнителя
  скиллов, а уведомление о решении нужно как раз тогда, когда исполнители
  недоступны (TAI-ADR-0053, «Отвергнуто»).
- **Условия и циклы в шаблонах** — граница spec: подстановка полей достаточна;
  разные тексты — разные правила с `on.when`.
- **Проверка типов по живому ядру** (`GET` каталога при каждом `:validate`) —
  проверка зависела бы от доступности ядра, а пакет проверяется и в CI без
  стенда. Снимок в сервисе обновляется вместе с закреплённой ревизией ядра;
  устаревший снимок ломает contract-тест, а не применение.
- **Двойной путь (таблица в коде как запасная, пока нет правил)** — два
  источника поведения; окно без уведомлений закрывается порядком выкатки
  (п. 8), а не кодом.
- **Изменяемые версии** (правка `spec` на месте) — уже созданные уведомления
  нельзя было бы связать с версией, по которой они созданы; хэш даёт
  идемпотентное повторное применение пакета без сравнения полей.

## Последствия

- Новый вид уведомления из события ядра — правка пакета `notify`, без выпуска
  сервиса (SC-004).
- Сервис знает о каталоге событий ядра: новый тип события доступен правилам
  после обновления снимка (выпуск сервиса с новой ревизией ядра).
- `NS_TASK_URL_TEMPLATE` уходит вместе с обработчиками; база ссылок — переменная
  установки пакета.
- Отступление по ст. VIII конституции (новая сущность) принято владельцем;
  взамен удаляется таблица событий в коде (C007).
- Шаблоны читают только поля события и проекции задачи; `displayName` —
  единственное обогащение, и оно не раскрывает ничего, кроме имени, уже
  видимого в каталоге ядра.
- Service account сервиса по-прежнему нуждается в `events.read`, `tasks.read`
  и `principals.read` (ADR-0002); новых прав в ядре не нужно.
