# ADR-0001. Каркас сервиса уведомлений: отправка, адресация, выбор каналов, доставка, веб-инбокс

Статус: предложено (2026-09-25), задача N006 (TASK-000415)

Основание: `specs/notifications/` суперпроекта (spec, plan — раздел «Дизайн»,
tasks — N006); ADR фичи (TAI-ADR-0048, N001) на момент решения ещё не влиты —
при расхождении с ними этот ADR правится под них.

## Контекст

Сервис уведомлений принимает уведомления от любого сервиса или скилла и доставляет
их людям по их настройкам и обязательным правилам организации (FR-001 — FR-004),
ведёт журнал доставки и отдаёт веб-инбокс без потерь при переподключении
(FR-012), не создавая дублей (SC-003). Сервис доменно-нейтрален (FR-013): тип,
заголовок, текст, ссылки и действия задаёт отправитель.

## Решение

### Процесс

API и воркер доставки — один процесс (бюджет staging из плана), воркер —
фоновый цикл asyncio. Несколько процессов допустимы: захват доставок и порядок
инбокса от этого не зависят (см. ниже).

### Аутентификация и права

Токены IAM проверяет только `platform_auth.TokenVerifier` (ADR-0030 суперпроекта):
точный audience `notification-service`, issuer и JWKS IAM. Scopes audience:

| Scope | Кому | Что даёт |
|---|---|---|
| `notifications:send` | сервисам, скиллам, правилам, людям | `POST /notifications`, журнал своих уведомлений |
| `notifications:read` | получателям | свой инбокс, поток, свои настройки |
| `notifications:admin` | администраторам организации | обязательные правила, журнал любого уведомления tenant'а |

Tenant — всегда IAM tenant из токена; значения из тела запроса авторитетными не
считаются. Без настроенного IAM сервис отвечает `503 verification_unavailable` —
закрыт, а не открыт.

### Адресация

Получатель (`recipient`) — один из трёх видов:

- `principal` — principal Control Plane (им назначаются решения);
- `role` + `workspaceId` — держатели роли в workspace (`GET /roles/{id}/principals?workspaceId=`
  ядра, задача N002) **и** групповые чаты, привязанные к этой роли в этом workspace;
- `group` — привязанный групповой чат (`channel_groups`).

Человек адресуется principal'ом ядра, а достигается IAM-identity, привязанной к
нему в ядре (`GET /principals/{id}/iam-bindings`, `IamBindingOut`): берётся
активная привязка с IAM tenant'ом отправителя и issuer'ом этого стенда. Инбокс,
настройки и адреса принадлежат этой IAM-identity — ровно тому `sub`, с которым
человек входит. Нет привязки в tenant'е отправителя — уведомление принято, а
доставка записана в журнал как `failed` / `recipient_has_no_identity`: чужой
tenant не получает уведомление даже при общем principal'е.

Каталог ядра читается service account'ом сервиса (client credentials →
`ServiceTokenProvider` → клиент `control_plane_client`), вне транзакции БД.
Неизвестный principal, роль или группа — `422 unknown_recipient`; ядро
недоступно — `503`, отправитель повторяет с тем же ключом.

### Дедупликация

`Idempotency-Key` обязателен. Уникальность — `(tenant, отправитель, ключ)`:
повтор с тем же телом возвращает первое уведомление (`200`) со всем его журналом,
с другим телом — `409 idempotency_conflict`. Конкурентные повторы сходятся на
уникальном ограничении БД.

Отличие от плана («`dedup_key` уникально в tenant»): ключ — собственность
вызывающего (FR-004), общее пространство ключей tenant'а вернуло бы одному
отправителю чужое уведомление.

### Выбор каналов

Для каждого человека и каждого настроенного канала, по порядку:

1. обязательное правило организации (`mandatory_rules`: шаблон типа × канал)
   выбирает канал независимо от настроек получателя и тихих часов;
2. иначе решает самая специфичная подходящая настройка получателя
   (`preferences`: шаблон типа × канал × вкл/выкл); без настройки канал включён;
3. канал выбирается, только если получатель на нём достижим (`web` — всегда,
   адресные каналы — при активном адресе в `channel_addresses`); обязательный
   недостижимый канал всё равно попадает в журнал как `failed` /
   `recipient_unreachable`, чтобы невыполненная обязанность была видна;
4. тихие часы (`quiet_hours`, в часовом поясе получателя) откладывают
   необязательную доставку в push-каналы до конца окна; инбокс никого не
   прерывает и не откладывается.

Шаблон типа — точный тип (`approval.requested`), префикс (`approval.*`) или `*`;
точный специфичнее префикса, длинный префикс — короткого.

### Журнал доставки и воркер

`deliveries` — уведомление × канал × получатель (человек или группа): статус
`pending → sending → delivered | failed`, число попыток, `next_attempt_at`,
последняя ошибка, внешний идентификатор. Воркер захватывает пачку
`FOR UPDATE SKIP LOCKED` с арендой (`locked_until`), отправляет вне транзакции
и записывает итог с фенсингом по номеру попытки: истёкшую аренду забирает другой
воркер, и поздний итог первого отбрасывается.

- Временная ошибка — повтор с экспоненциальной задержкой (5 с × 2ⁿ, не больше
  часа), не больше 8 попыток, затем `failed` / `retries_exhausted: …`.
- Постоянная ошибка — `failed` сразу. «Адрес мёртв» (`RecipientUnreachable`:
  почтовый ящик отвергнут, бот заблокирован) дополнительно выключает адрес или
  группу — канал перестаёт выбираться до повторной установки адреса.
- Доставки независимы: отказ одного канала или адреса не задерживает другие.
  Доставки одного получателя в одном канале идут по порядку создания.

Канал — адаптер с общим интерфейсом `send(OutboundMessage) → SendResult`;
новый канал не меняет контракт отправки (FR-003).

### Веб-инбокс и поток

Канал `web` пишет в `inbox_items`. У каждой записи — `seq`, растущий в пределах
получателя и выдаваемый под транзакционной advisory-блокировкой получателя:
записи становятся видимы строго в порядке `seq`, поэтому «всё после `seq` N» —
надёжная точка возобновления.

`GET /me/notifications/stream` — SSE: `id` события — `seq`. Переподключение с
`Last-Event-ID` (заголовок браузера или параметр `lastEventId`) сначала отдаёт
всё пропущенное по порядку, затем продолжает вживую. Без него поток начинается
с текущего конца инбокса (всё прежнее — в `GET /me/notifications`). Поток
закрывается, когда истекает открывший его токен: клиент переподключается со
свежим токеном и `Last-Event-ID`, ничего не теряя. Пробуждение
потока — внутри процесса; доставки другого процесса подхватываются опросом
(`NS_INBOX_POLL_SECONDS`, по умолчанию 5 с).

### Почта

Канал `email`: SMTP (`NS_EMAIL_MODE=smtp`), на staging — только запись в лог
(`log`), либо выключен (`disabled`). IAM не хранит почтовых адресов, поэтому
адрес задаёт сам получатель в настройках; ответ 5xx на получателя выключает
адрес, 4xx и недоступность сервера — временные ошибки.

### Хранилище

Таблицы (миграция `0001`): `notifications`, `deliveries`, `inbox_items`,
`preferences`, `mandatory_rules`, `quiet_hours`, `channel_addresses`,
`channel_groups`.

Сверх перечня плана: `inbox_items` (инбокс с `seq` отдельно от журнала,
который общий для всех каналов) и `channel_addresses` (адреса адресных каналов).
Из перечня плана пока не созданы `event_cursors` и `callbacks`: их форма
определяется SDK потребителя событий (N003, хранилище курсора) и кнопками
Telegram (N007) — таблицы добавят миграции этих задач (`event_cursors` и
`handled_events` — миграция `0002`, [ADR-0002](0002-control-plane-event-consumer.md);
`callbacks` — `channel_callbacks` миграции `0003`, [ADR-0003](0003-telegram-channel-and-decisions.md)).

### API (`/api/v1`)

| Метод и путь | Scope |
|---|---|
| `POST /notifications` (`Idempotency-Key`) | `notifications:send` |
| `POST /skills/notify.send` — скилл `notify.send@1` ([ADR-0004](0004-notify-send-skill.md)) | `notifications:send` |
| `GET /notifications/{id}` — уведомление и журнал доставки | `notifications:send` (своё), `notifications:admin` |
| `GET /me/notifications` (`unreadOnly`, `limit`, `cursor`) | `notifications:read` |
| `GET /me/notifications/stream` (SSE, `Last-Event-ID`) | `notifications:read` |
| `POST /me/notifications/{id}:read`, `POST /me/notifications:read-all` | `notifications:read` |
| `GET`, `PATCH /me/notification-preferences` | `notifications:read` |
| `GET`, `POST /mandatory-rules`, `DELETE /mandatory-rules/{id}` | `notifications:admin` |

Ошибки — конверт `{"error": {"code", "message", "details"}}`, как в ядре (у маршрута
скилла — форма skill-sdk с `retryable`, ADR-0004).
`GET /healthz` — публичный (метка `authz: public` в коде).

## Последствия

- Адресация ролью заработает, когда ядро отдаст `GET /roles/{id}/principals`
  (N002); до этого ядро отвечает 404 и сервис — `422 unknown_recipient`.
  Contract-тест адаптера каталога собран на моделях API ядра (`PageOut`,
  `PrincipalOut`, `IamBindingOut`) — при появлении маршрута его ответ сверяется
  с тем же тестом. (Маршрут появился в N002: ответ — страница `RoleHolderOut`,
  адаптер вызывает `ControlPlaneClient.list_role_holders`, см. ADR-0002.)
- Эндпоинты привязки групп (`/workspaces/{id}/channel-groups`) и Telegram — N007;
  здесь группы только читаются при адресации. (Сделаны в N007, см.
  [ADR-0003](0003-telegram-channel-and-decisions.md).)
- Почтовый адрес не подтверждается: получатель может направить свои же
  уведомления на чужой ящик. Подтверждение адреса — отдельная задача, если
  почта станет основным каналом.
