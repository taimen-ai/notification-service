# ADR-0002. Потребитель событий ядра: решения и проваленные проверки как уведомления

Статус: предложено (2026-09-25), задача N008 (TASK-000417)

> **Частично заменено [ADR-0005](0005-notification-rules-as-data.md)
> (2026-09-27, `declarative-cycle` C003).** Таблица «События → уведомления»,
> фильтр потребителя (`types = approval., task.verification_failed`) и
> `NS_TASK_URL_TEMPLATE` уходят из кода: какие события становятся
> уведомлениями, кому, каким текстом, с какими кнопками и что их закрывает —

> дедупликации (ключи `control-plane:approval:<id>`, `control-plane:event:<id>`
> сохраняются) и закрытые действия действуют. Код переходит в C007; до его
> выкатки работает таблица ниже.

## Контекст

Ядро пишет в журнал, какого решения ждёт (`approval.requested` v2: кто решает, по
какой работе, кто просит, workspace), чем оно кончилось (`approval.approved`,
`rejected`, `cancelled` v2) и что проверка приёмки провалилась
(`task.verification_failed`, M1.6). Людям об этом сообщал харнесс владельца
вручную. Сервис уведомлений должен сам читать эти события и звать людей, не
создавая дублей при повторной доставке события и после перезапуска.

## Решение

### Чтение журнала

Потребитель — `EventConsumer` из SDK ядра, в том же процессе, что API и воркер
доставки (фоновая задача asyncio): фильтр `types = approval., task.verification_failed`,
весь tenant service account'а или поддерево `NS_EVENTS_WORKSPACE_ID`; пробуждение
по WebSocket `/events/ws` (extra `control-plane-client[events]`), опрос раз в
`NS_EVENTS_POLL_SECONDS` (30 с). Курсор и журнал обработанных событий — таблицы
SDK `event_cursors` и `handled_events` в БД сервиса (миграция `0002`), имя
потребителя — `notification-service`.

При первом запуске (курсора ещё нет) чтение начинается с конца журнала
(`NS_EVENTS_START=latest`): новая установка не рассылает уведомления об истории.
`earliest` — для восстановления, когда нужно пройти весь хранимый журнал.

Ядро отказывает в подписке (нет `events.read`, чужой credential) — потребитель
останавливается с записью в лог, API и доставка продолжают работать. Сбой
страницы, сети или ядра — повтор с того же курсора (поведение SDK).

### Кто отправитель

Уведомления из событий отправляет сам сервис — своим service account'ом, тем же
путём `NotificationSender`, что и `POST /notifications`: те же адресация, выбор
каналов, журнал доставки. Tenant и `sub` отправителя берутся из токена, который
сервис предъявляет ядру, проверенного `platform_auth.TokenVerifier` с audience
`control-plane`. Отсюда допущение: IAM tenant service account'а — это IAM
tenant людей того tenant'а ядра, события которого он читает.

### События → уведомления

Заменено правилами уведомлений (ADR-0005 п. 8) — таблица описывает поведение
до перехода и три правила пакета `notify`, которые его переносят.

| Событие | Что делает сервис |
|---|---|
| `approval.requested` | уведомление типа `approval.requested`: назначенному principal'у (`assignedPrincipalId`), иначе держателям роли `requiredRoleId` в `workspaceId` (из payload, иначе из конверта). Заголовок — «Нужно решение: <publicId> <title>», в тексте — кто просит (имя из `GET /principals/{id}`) и комментарий; ссылка на задачу по `NS_TASK_URL_TEMPLATE`; действия `approve` и `reject` с `data = {kind: "approval.decide", approvalId, decision}` — их исполняет канал с кнопками (Telegram, N007). Для событий версии 1 (без `taskPublicId`/`taskTitle`) задача дочитывается `GET /tasks/{id}` |
| `approval.approved`, `approval.rejected`, `approval.cancelled` | действия уведомления об этом approval закрываются: `actionsClosedAt` и `actionsOutcome = {status, by, channel, at}`. Побеждает первое закрытие; нет уведомления — ничего |
| `task.verification_failed` | уведомление типа `task.verification_failed` владельцу задачи (`ownerId`), без владельца — исполнителю (`assigneeId`): какая проверка и почему не прошла, вернулась ли задача в работу или ждёт человека. Без действий |
| прочие `approval.*` (исполнение исходов) | пропускаются |

Тексты — нейтральные слова ядра (решение, задача, проверка), без понятий домена;
поля домена приходят из задачи (`taskTitle`) и комментария (FR-013). Получатель
отключает любой из типов в своих настройках, как любое уведомление.

Адресат не найден в каталоге ядра (`422 unknown_recipient`), payload не
соответствует схеме, у задачи нет ни владельца, ни исполнителя — событие
пропускается с записью в лог: повтор этого не исправит, а задержал бы все
следующие события. Каталог или ядро недоступны — обработчик падает, и SDK
повторяет событие.

### Ровно одно уведомление

Два независимых барьера:

1. SDK записывает id обработанного события вместе с курсором в одной транзакции:
   повторно доставленное событие не обрабатывается.
2. Ключ дедупликации уведомления выводится из события — `control-plane:approval:<approvalId>`
   для запроса решения, `control-plane:event:<eventId>` для проверки. Сбой между
   фиксацией уведомления и записью события приводит к повторной обработке, и
   `accept` возвращает уже созданное уведомление. Если текст за это время изменился
   (например, имя просящего), `409 idempotency_conflict` значит «уже отправлено».

Ключ по `approvalId` ещё и связывает решение с запросом: закрытие действий
находит уведомление по нему.

### Закрытые действия

`notifications.actions_closed_at` и `actions_outcome` (миграция `0002`) — общий
механизм, не только для approvals: действия уведомления больше не применимы, и
вот почему. API отдаёт их в `NotificationOut` и `InboxItemOut` (`actionsClosedAt`,
`actionsOutcome`) — поля только добавлены. Воркер не передаёт каналу закрытые
действия: доставка, ушедшая после решения (повтор, тихие часы), приходит без
кнопок.

## Последствия

- Решение из Telegram (N007) опирается на это: кнопки строятся из `actions`, а
  при закрытии канал обновляет уже отправленные сообщения по журналу доставки
  уведомления. Веб-инбокс видит закрытие при следующем чтении списка; поток SSE
  несёт только новые записи.
- Закрыть действия своего уведомления через API отправитель пока не может: это
  делает только потребитель событий. Понадобится другим отправителям — отдельный
  маршрут.
- Service account сервиса должен иметь в ядре `events.read` (tenant или
  workspace), `tasks.read` и `principals.read` — перечень plan'а (bootstrap, N009).
- Адресация ролью (ADR-0001) теперь идёт через `ControlPlaneClient.list_role_holders`
  (`GET /roles/{id}/principals`, модель `RoleHolderOut`); contract-тест сверяет
  адаптер с этой моделью.
