# ADR-0003. Канал Telegram: привязка, группы, решения кнопками

Статус: предложено (2026-09-25), задача N007 (TASK-000416)

Основание: `specs/notifications/` суперпроекта (spec — FR-003, FR-005, FR-006,
FR-007, SC-001, SC-003, SC-004, сценарии 1 и 3; plan — «Исследование» п. 6, 8 и
«Дизайн»; tasks — N007), TAI-ADR-0048, TAI-ADR-0050 (канал как способ входа);
контракты соседей — IAM `channels/routes.py` и `channels/schemas.py` (N004),
CP-ADR-0070 (scope `control-plane:decide`, `purpose_ref`, N005).

## Контекст

Каркас (ADR-0001) доставляет уведомления в инбокс и почту, потребитель событий
(ADR-0002) строит уведомления о решениях с действиями `approval.decide`. Нужен
канал, где человек получает сообщение с кнопками и решает, не открывая веб:
решение — от его имени, с его правами, повторное нажатие ничего не меняет, без
действующей привязки и права решение не принимается.

## Решение

### Бот и вебхук

Один бот на стенд (`NS_TELEGRAM_BOT_TOKEN`). Обновления Bot API приходят на
`POST /channels/telegram/webhook` (вне `/api/v1`, метка `authz: public` в коде):
единственное доказательство, что их прислал Telegram, — секрет регистрации
вебхука в заголовке `X-Telegram-Bot-Api-Secret-Token`, сравнивается за
постоянное время. Без секрета в настройках вебхук отвергает всё (`401`), без
токена бота маршрута нет (`404`). На принятое обновление вебхук отвечает `200`
даже при сбое обработки (с записью в лог): иначе Telegram повторял бы одно и то
же обновление; человек, чьё нажатие не удалось, нажимает ещё раз.

### Личная привязка

1. Человек в вебе получает у IAM одноразовый код (`channel-link-intents`, N004)
   и шлёт боту `/start <код>` (или открывает ссылку `t.me/<бот>?start=<код>`).
2. Сервис как адаптер канала — service account с scope `iam:channel-links` в
   audience `iam` (`NS_IAM_CHANNEL_AUDIENCE`, `NS_IAM_CHANNEL_SCOPE`) —
   вызывает `POST /api/v1/tenants/{t}/channel-links:confirm {channel: telegram,
   code, externalSubject}`. `externalSubject` — id отправителя, в личном чате он
   же id чата: IAM привязывает ровно тот аккаунт, который прислал код. Tenant
   пути — IAM tenant service account'а из его токена (проверен
   platform-auth-sdk); отсюда, как и в ADR-0002, один IAM tenant на установку.
3. Ответ IAM (`ChannelLinkView.principalId`) становится адресом `telegram`
   человека в `channel_addresses`: `address` — id личного чата. По нему же
   вебхук находит, кто нажал кнопку (индекс `(channel, address)`). Если этот
   аккаунт раньше был адресом другого человека tenant'а, тот адрес выключается.

Отказы IAM (неверный, чужой, использованный или просроченный код; аккаунт уже
привязан; провайдер выключен; лимит) бот объясняет человеку текстом, не
раскрывая больше, чем код ответа IAM.

`/unlink` в личном чате выключает адрес (`unlinked_by_user`): сообщения больше
не приходят, кнопки не действуют. Отозвать привязку в самом IAM адаптер не
может — у IAM нет такого маршрута для service account; бот отправляет
человека в веб (`channel-links/{id}:revoke`). Вернуть выключенный так адрес
можно только новой привязкой: отвязка — шаг безопасности, и `/start` без кода
его не отменяет. Адрес, выключенный блокировкой бота, `/start` без кода
возвращает — Telegram присылает его, когда человек разблокирует бота.

### Группы

`POST /api/v1/workspaces/{id}/channel-groups {channel, roleId?}`
(`notifications:admin`) выдаёт одноразовый код (10 минут,
`NS_CHANNEL_GROUP_CODE_TTL_SECONDS`, в базе — только хэш, таблица
`channel_group_intents`), команду `/start@<бот> <код>` и ссылку
`t.me/<бот>?startgroup=<код>`, которая добавляет бота в группу и шлёт команду.
Команда в группе создаёт `channel_groups` (чат ↔ workspace и, если задана, роль);
повторная привязка того же чата переносит его. Код, как и личный, знают только
администратор и сервис. `GET` — привязки workspace (с выключенными),
`DELETE …/{groupId}` — выключает (`unlinked_by_admin`).

Группа получает уведомления, адресованные ей (`recipient.kind = group`) или роли
в её workspace (ADR-0001). Кнопку в группе может нажать любой, но решение
принимается только от имени нажавшего: у него должна быть своя личная привязка,
и ядро проверяет его право и пригодность (сценарий 3, п. 3).

### Сообщения

Канал `telegram` (адаптер `TelegramChannel`, `push`, нужен адрес): HTML Bot API,
заголовок жирным, текст, ссылки; длинный текст обрезается так, чтобы ссылки и
итог остались в пределах 4096 символов. Действия с `data.kind = approval.decide`
становятся inline-кнопками, `callback_data = a:<id уведомления>:<номер действия>`
(≤ 64 байт); прочие действия канал не исполняет и не показывает.
`external_id` доставки — `<chat_id>:<message_id>`: по нему находятся сообщения
для обновления и проверяется, что нажата кнопка сообщения, отправленного этим
сервисом в этот чат для этого уведомления.

Ошибки Bot API → журнал доставки: `403` (бот заблокирован, удалён из группы) и
`400 chat not found` — адрес мёртв (`RecipientUnreachable`: адрес или группа
выключаются), `429` и `5xx` — повтор, группа, ставшая супергруппой
(`migrate_to_chat_id`), переезжает на новый id и повторяется, неверный токен
бота — повтор (ошибка конфигурации), прочие `400` — постоянный отказ. Кроме
того, вебхук сам слушает `my_chat_member`: бот заблокирован в личном чате —
адрес выключен (`bot_blocked`), удалён из группы — группа выключена
(`bot_removed`).

### Нажатие кнопки

1. Кнопка разбирается и сверяется с журналом доставки (сообщение этого чата для
   этого уведомления); иначе — «кнопка больше не действует».
2. Нажатие записывается в `channel_callbacks` по id callback'а Telegram. Повторно
   доставленное обновление с тем же id получает записанный ответ и ничего не
   вызывает. Исход «недоступно» (IAM или ядро не ответили, лимит частоты) не
   записывается окончательно: тот же callback решается заново.
3. Нажавший — активный адрес `telegram` с его id **в tenant'е уведомления**:
   человек, привязанный в нескольких tenant'ах, решает там, откуда пришло
   сообщение. Нет адреса — отказ «не привязан».
4. Действия уже закрыты — ответ «Уже решено: <итог>» без обращений к IAM и
   ядру; это же отвечает второе нажатие после решения. Затем approval
   дочитывается service account'ом (`GET /approvals/{id}`): уже не `pending`
   (решено в вебе, событие ещё не дошло) — тот же ответ, и действия закрываются.
   Дочитывание — подсказка: не прочитать можно, решение проверит ядро.
5. Обмен в IAM: `POST …/channel-assertions:exchange {channel: telegram,
   externalSubject, purposeRef: "approval:<uuid>"}` — ровно в форме, которую
   разбирает ядро (CP-ADR-0070). `404 channel_account_not_linked` (отозвано в
   вебе) выключает и местный адрес (`iam_link_revoked`); выключенный провайдер,
   неактивный или не-человек — отказ с объяснением.
6. Решение: `POST /api/v1/approvals/{id}:approve|:reject` с токеном человека и
   `Idempotency-Key` = id callback'а. `403` (нет права, не назначен) — «нет
   права», `409 approval_already_decided` — «уже решено» с итогом, прочее —
   «недоступно».
7. Ответ человеку — `answerCallbackQuery` (отказы — всплывающим окном). После
   решения действия уведомления закрываются с итогом `{status, by, channel:
   telegram, at}`, не дожидаясь события ядра; событие потом ничего не меняет
   (побеждает первое закрытие, ADR-0002).

### Обновление сообщений итогом

`NotificationSender.close_actions` сообщает каналу о закрытии, которое победило
(`on_actions_closed`), — и для решения кнопкой, и для события ядра
(`approval.approved|rejected|cancelled`: решено в вебе, отменено). Канал правит
каждое доставленное сообщение уведомления (`editMessageText` без клавиатуры):
тот же текст и строка итога — «✅ Одобрено — <имя>, через Telegram». Правка —
по возможности: сбой пишется в лог, а оставшаяся кнопка на нажатие отвечает
итогом (п. 4). Доставки, ушедшие после закрытия, кнопок не несут (ADR-0002).

### Хранилище

Миграция `0003`: `channel_group_intents`, `channel_callbacks` (дедуп нажатий из
перечня plan'а — `callbacks`), индекс `channel_addresses (channel, address)`.

## Последствия

- Решение из Telegram работает, когда настроены IAM (адаптер: `NS_IAM_URL`,
  `NS_SERVICE_CLIENT_ID|SECRET`, JWKS) и Control Plane; без них бот объясняет,
  что сервис недоступен. Service account должен иметь в IAM scope
  `iam:channel-links` в audience `iam`, в ядре — `approvals.read`
  (дочитывание) — перечень plan'а для bootstrap (N009); там же регистрация
  вебхука (`setWebhook` с `secret_token`).
- Комментарий к решению из Telegram пока не собирается: кнопка решает без
  комментария. Сбор комментария (ответ на сообщение) — отдельная задача.
- Отзыв привязки в вебе сервис узнаёт при следующем нажатии (п. 5): до него
  сообщения в этот чат ещё уходят. События IAM `channel_link.revoked` сервис не
  читает — у IAM нет для этого потребительского контракта.
- Исход gate-решения из канала исполняется с правами токена канала
  (CP-ADR-0070, «Последствия»): действия, которым нужно больше, падают и
  повторяются из веба.
